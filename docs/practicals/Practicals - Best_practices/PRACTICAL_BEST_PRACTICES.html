Best Practices 1: Coding for Trustworthy Bioinformatics

Author

Kaisa Thorell, Tor Kling

Published

September 23, 2026

Introduction

For this practical we will start analyzing bioinformatic datasets, applying the best practices and habits that make our code reproducible, resilient and intepreteable for others. The practical is split into two subsections

Practical 1: Scripting for Genome Selection

Scenario

You have received assembly-quality summaries for a set of bacterial isolates. Someone wrote a Bash script to select genomes for downstream comparative genomics. The script runs and produces a list of “good” assemblies. Your task is to decide whether that list deserves to be trusted, then improve the analysis without accidentally changing its intended rule.

Learning Objectives

By the end of this practical, you should be able to:

  • Recognise hidden assumptions and fragile coding practices.
  • Improve readability, parameterisation and error handling in a Bash analysis.
  • Document an analysis so another person can rerun it.

Files – download zipped file from Canvas

Practical_1/
└──hands_on/
    ├── bad_analysis.sh
    ├── README_STARTER.md
    └── data/
        ├── assembly_stats.tsv

The tables contain sample ID, assembly size (bp), number of contigs, N50 (bp), GC content (%), completeness (%) and contamination (%). Treat these as summary statistics supplied by upstream tools; today the focus is the code that uses them.

Part 1 — Crime scene investigation

Run the analysis from the hands_on directory. Do not edit it yet. In pairs, list as many concerns as you can. For each concern, label it R = readability, P = reproducibility, B = robustness, or S = scientific correctness.

./bad_analysis.sh
cat results.txt

Key questions

  • What do columns 3, 6 and 7 represent? How do you know?
  • Why are the thresholds 100, 95 and 5? Are the inequalities part of the scientific definition?
  • What happens if the input file is missing or empty?
  • What assumption does grep -v sample make about the header and sample names?
  • Could the temporary file overwrite something important?
  • Does the script notice NA values or biologically implausible assembly statistics?
  • What does “done” tell you about whether the analysis succeeded?

Part 2 — Make it understandable

Create analysis.sh from bad_analysis.sh. Improve variable names, formatting and comments. Keep the output scientifically identical for now. Make the QC criteria visible near the top of the script. Add comments only where they explain intent or assumptions.

Checkpoint: your partner should be able to explain every command and identify every QC threshold without decoding a one-liner.

Part 3 — Break your program

Try cases that should not silently succeed. Improve the script so failures produce a useful message and non-zero exit status.

  • nonexistent input file
  • empty input file
  • wrong number of arguments
  • output directory that does not yet exist
  • a filename containing spaces

Consider whether set -euo pipefail is appropriate. If you use it, be able to explain what each option protects against, and what it does not check.

Part 4 — Reproducibility swap

Complete the README. Swap project directories with another pair. Without verbal instructions, the other pair should be able to answer:

  • What does the analysis do?
  • How do I run it?
  • What inputs and parameters are required?
  • What output is produced?
  • What QC rule is applied?
  • Which assumptions or sanity checks are not covered by the script?
Bonus — Make it reusable

Change the script so input and output are command-line arguments. Then make the QC thresholds parameters, with sensible defaults if you are comfortable doing so. This could for example be done with the OPTARGS described in CLI practical 4. Its also possible to do it using positional arguments (e.g., $1 for the input file, $2 for the output file, $3 for the first QC threshold, etc.)

./analysis.sh data/assembly_stats.tsv results/selected_genomes.txt or ./analysis.sh -a data/assembly_stats.tsv -o results/selected_genomes.txt

Optional extension: ./analysis.sh data/assembly_stats.tsv results/selected_genomes.txt 100 95 5

Do not use absolute paths tied to your own computer. Decide whether your script should create the output directory or require it to exist, and document that choice.

Practical 2: From Pseudocode to Shareable Workflow

Scenario

You have a tab-separated annotation table of genes involved in antimicrobial resistance from a set of bacterial genomes. Each row describes one annotated gene and contains three columns: strain, gene, and product.

strain  gene    product
S01 gyrA    DNA gyrase subunit A
S01 blaTEM  beta-lactamase TEM
S02 tetA    tetracycline efflux protein
Task:

You want to find which bacterial strains contain a particular target gene. In the end the

  • strain names should be saved to a file
  • how many strains that contain the target gene should be reported

Work in pairs. The instructor will tell you the target gene. Do not start by writing Bash commands.

Part 1 - Write pseudocode first

Describe the analysis as a sequence of plain-language steps. Your pseudocode should be understandable to another student even if they have not seen your commands.

Before coding, swap pseudocode your classmate. Can they understand the plan without asking what you meant? Revise anything ambiguous.

Part 2 - Translate your plan into Bash

Now translate each pseudocode step into commands that we’ve introduced in the previous practicals. Useful commands may include grep, cut, sort, uniq, wc and awk.

Keep the solution simple, remember the tips about good coding practice. The goal is not to write the shortest possible command.

Save your commands in a small bash script. As you work, consider:

  • Can another person tell what biological question the script answers?
  • Is the target gene easy to find and change in the script?
  • Does the script create a clearly named output file?
  • Are there comments where they help explain the purpose or reasoning?
  • Can you inspect an intermediate result if something looks wrong?

Part 3 - Swap scripts

Give your script to your classmate. Do not explain it at first. The receiver should run and read the script and answer:

  • What biological question does the script answer?
  • Which gene is being searched for?
  • What output does it produce?
  • Does it count genes or unique samples?
  • Could you change the target gene without rewriting the workflow?
  • Is any line difficult to understand?
  • What is one thing that is particularly clear, and one thing you would improve?

Return the script and feedback. The original author may make one or two improvements.

Bonus - Predict before you test

If you have reached here before it’s time to reconvene, let us know and we will provide a surprise annotation table. Before running your script, inspect the file and write down which samples you think should count as containing the target gene. The intended question is:

Which samples have an exact match to the target gene in the gene column?

Then run your script on the surprise table and compare the output with your prediction.

If they differ, investigate why. Look especially for:

  • the same gene occurring more than once in one sample
  • similar but non-identical gene names
  • the target gene name appearing in the product description rather than the gene column
  • capitalization differences
  • whether your command searches the whole line or a particular column

Final wrap up - Discuss and revise

With your partner, discuss what the surprise dataset revealed. If necessary, revise your script so that it answers the stated biological question more precisely.

Be ready to explain one design choice to the class.
